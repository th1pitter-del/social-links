2. BUG FOUND AND FIXED WHILE DOING IT: ROWS WERE DEAD
=====================================================================
DropdownMenuItem asChild + Slot hands the item's props - role, tabIndex, id,
the pointer/keyboard handlers and the item ref - to the child component. NavRow
dropped them, so the menu rendered unhighlightable divs and ArrowDown threw:
    TypeError: Cannot read properties of null (reading 'focus')
        at DropdownMenuContent ... (site-nav.tsx:148)
Fix: NavRow spreads {...rest} and forwards ref to the actual DOM node in each
of its three branches. Every row now reports role="menuitem", ArrowUp/Down/End
move the highlight, and activation works.

4. HOVER / FOCUS SURFACES (root cause, restated)
=====================================================================
In dark mode --accent equals --popover (#1d1e1b), so the shared dropdown item's
focus:bg-accent is invisible against the panel, and bg-foreground/10 computes to
transparent. The header rows therefore spell out the design-spec hover tokens:
    hover:bg-[#f0f1ea] focus:bg-[#f0f1ea]
    dark:hover:bg-[#2a2b27] dark:focus:bg-[#2a2b27]
Measured this round against the panel colour:
    light: panel rgb(255,255,255) -> hover rgb(240,241,234)
    dark:  panel rgb(29,30,27)    -> hover rgb(42,43,39)
Both verified with a real pointer hover and with keyboard focus (Radix focuses a
row on pointer-enter, so the focus: variant is what actually paints).

Partner colours survive the hover: the shared item styles every descendant on
focus (focus:text-accent-foreground), which used to turn the label and icon
white. The tone classes now carry "!" and the icon carries text-inherit!:
measured on "Baixar vídeo" while hovered, label and icon both rgb(76,186,149);
the compressor link keeps rgb(81,130,239).

10. HOMEPAGE: THE PRODUCT IS NOW DEMONSTRATED, NOT DESCRIBED
=====================================================================
The identity, palette, fonts and components are the ones in
docs/design-spec.md. No new dependency was installed: the motion is CSS
transitions/keyframes plus four small client islands.

src/components/motion/reveal.tsx        (new)
 - useReducedMotion() reads (prefers-reduced-motion: reduce) through
   useSyncExternalStore, so there is no effect-time setState and the value is
   correct on the first client render.
 - useInView() gates every loop on visibility with IntersectionObserver, using a
   useState callback ref (this project's lint rules forbid reading a ref during
   render, and the flag has to re-render anyway).
 - <Reveal> fades and lifts a section in once. motion-reduce: classes put the
   content in place immediately, in CSS, before JavaScript runs.

src/components/motion/demo-cycle.tsx    (new)
 - useDemoCycle({phaseCount, intervalMs}) is one clock shared by every
   demonstration. It advances only while the demo is on screen, playing, not
   being steered, and the visitor has not asked for reduced motion.
 - Pointer steering is mouse-only (pointerType === 'mouse'), so a dragging
   finger never fights the page scroll, and it mirrors the axis in RTL by
   reading getComputedStyle(node).direction.
 - <DemoStage> owns the callback ref and the pointer handlers in one place;
   <DemoShell> wraps that in the frame every demo shares: a label that says it
   is an example, one dot per phase, pause/play and replay, and an aria-live
   line that names the phase.
 - The dots are 20x20px tap targets and are visible at every width. They were
   hidden below sm: before, which left a phone with no way to reach a specific
   phase once the loop was paused.

src/components/home/unlock-demo.tsx     (new) - hero
 - The real unlock card's own layout, tokens and wording (it reuses the
   unlock.* messages) walked through the six phases a visitor actually goes
   through: idle, session open, each step verified, content delivered.
 - The progress fill is width-based with role="progressbar", not the shadcn
   <Progress> indicator, because that one slides with translateX and would fill
   from the wrong edge in Arabic. It also drops its transition when it returns
   to zero, so the bar never reads "full" while the counter says "0 of 3".
 - The call-to-action slot cross-fades through the three labels the real card
   uses in order - start, open step, unlock, then "Open your content" once
   delivered - inside a fixed-height, aria-hidden box so the card never jumps

src/components/home/step-rail.tsx       (new) - replaces three identical cards

src/components/home/flow-diagram.tsx    (new)

15.1 THE FAKE NUMBERS WERE REAL CODE, AND ARE GONE
Both overviews drew an "action mix" from fixed fractions of the view count:
0.42 / 0.28 / 0.18 / 0.12, each floored at 1, under a caption that said
"Estimated by recent activity". Views have no relationship to which action a
visitor completes, so every one of those four bars was invented, and the floor
of 1 drew a full-height bar even at zero completions. The same eight lines were
copy-pasted into the admin overview.

src/lib/action-mix.ts (new) counts unlockActionCompletion rows grouped by the
platform that owns each action (platform label, then the action's own label),
sorts descending and takes the top five. src/app/dashboard/page.tsx and
src/app/admin/page.tsx both call it - the creator scope passes ownerId, the
admin scope passes nothing and so sees every owner. When there are no
completions the panels now say so ("No visitor has completed an action step
yet") instead of drawing four confident bars.
Measured, from real rows: the creator panel read "Bluesky 5 · 50%, Discord 4 ·
31%+ · Custom action 1 · 10%, 10 etapas concluídas" for a seeded link whose
completions were 5/4/1, and the admin panel read Bluesky 5 · 38% / Discord 4 ·
31% / YouTube 3 · 23% / Custom action 1 · 8% of 13 - the YouTube 3 being the
pre-existing test link "ddddd", owned by another account. Percentages now sum
